For substantive/parallel-heavy work in this engagement (e.g. multi-file consolidation, recompose waves), use **ultracode = the Workflow tool**, structured with the **GSD mentality**: a **planning workflow** (map/discover → a PLAN under `.planning/`), then an **execution workflow** (apply + verify). Do NOT fall back to a single ad-hoc `Agent` call for this kind of work.

**CRITICAL — GSD is a MENTALITY, not the literal agents.** Drive your OWN worker agents inside the Workflow script (`agent(...)` with the default or `Explore` agentType). Do **NOT** spawn the `gsd-planner` / `gsd-executor` `agentType`s directly — the user said "we don't use the gsd planner directly here; we just utilize its directives and overall gsd framework mentality to drive our workflows." When I spawned a real `gsd-planner` it overstepped and edited implementation files instead of only planning. Use the framework's *discipline* (plan→execute split, gates, goal-backward verification), not its subagents.

**Why:** standing directive from the engagement brief; the user enforces the plan→execute split deliberately and wants controllable workers, not opaque GSD agents.

**The TWO-PASS design-review flow (the disciplined shape, operator-chosen).** For a design-feedback cycle: (1) **Explore + Plan** — ONE workflow: parallel read-only explorers diagnose each area (file:line + root cause + approach) → a planner writes a sequenced `PLAN.md` (workstreams, order, operator decisions); no code changes. (2) **Operator decisions** — surface the genuine gray-area forks via `AskUserQuestion` (recommended defaults); default the rest. (3) **Execute in TWO passes**, each its own workflow: **Pass 1 = correctness/infra first** (the reviewer + bug fixes that make the review surface itself correct — save/deletion, stage-incremental generation, binding bugs) → **operator re-reviews the corrected reviewer**; **Pass 2 = the substantive design change** (tokens/components), reviewed in both modes. Rationale: "re-review the corrected reviewer before the design churn." (4) Each Execute ends with a **structural** verify (typecheck/tests/emitted values), but the **OPERATOR is the only fidelity gate** — sub-agent screenshot verdicts are never trusted, and the Playwright sandbox can't hydrate Turbopack (HMR WS blocked) so interactive checks are the operator's. Full write-up: `tmmaf/.planning/design-drift-remediation/stage1-feedback-round1/SESSION-HANDOFF.md` §0.

**AUTO-ADVANCE through passes when the operator can't review yet (operator directive 2026-06-08).** The pass split is for YOUR rigor, not a per-pass approval gate. When the operator has given a batch of feedback and the next review can only happen after the work lands (e.g. the designs are still being updated, or a tooling/review-page update must finish first), **move through ALL the passes automatically — detect → fix → tooling/template-sync — without stopping to ask between them.** Only pause for the operator when you hit a genuine un-defaultable brand/UX fork, or when they explicitly asked to wait. Default to driving: make DS-grounded judgment calls yourself, document them, and hand a single consolidated result for review at the end. Self-verify between your own passes (that's your discipline, not waiting on the operator).

**How to apply:** >trivial chunk → Explore+Plan workflow, then Execute workflows using your OWN agents; chain them automatically when the operator can't review mid-stream. Keep the main session lean; sub-agents capture/execute, the operator stays the final gate. Always verify agent findings yourself (greps/typecheck/read emitted values) — they under-report. **Tell workflow agents AND yourself to use `graphify query/explain/path` for codebase exploration instead of re-grepping the same symbols every workflow — it saves context (see [[project_graphify_scope_code_and_docs]]).** Relates to [[feedback_fix_properly_system_wide]], [[feedback_evolve_skill_as_we_progress]], [[project_review_loop_gated_design_tool]], [[feedback_visual_analyzers_weak]].
